## 1. 设计目标

为 z-cache 提供**服务端原语 + 客户端高层 API** 的分布式锁能力，使 z-msg、z-task 等依赖方可通过简洁的 tryLock/unlock 调用获得互斥保证，对标 Redis 分布式锁的语义（[Redis 官方分布式锁指南](https://redis.io/docs/manual/patterns/distributed-locks/)）。

### 1.1 设计原则

1. **架构正确**：服务端（z-cache-core）只暴露原语 `SET NX PX` + Lua EVAL；高层 API（`tryLock/unlock/renew`）由 z-cache-client 实现。
2. **零新增依赖**：完全基于 z-cache 现有 `SET NX PX` 与 Lua EVAL，不引入 Redisson 等第三方库（依据调研结论 §4.1）。
3. **可演进**：1.3.0 单节点 Redlock 等价能力先行；2.0.0 集群化后扩展多节点 Redlock。
4. **API 易用**：tryLock 返回 Lock 句柄（包含 ownerId + fencing token），unlock/renew 通过句柄调用，避免误删他人锁。

## 2. 公共 API 定义

### 2.1 顶层接口 `DistributedLock`

```java
package com.zifang.z.cache.client.lock;

/**
 * z-cache 分布式锁高层 API。
 *
 * <p>典型用法：
 * <pre>{@code
 * try (ZCacheClient client = new ZCacheClient("localhost", 16379)) {
 *     client.connect();
 *     DistributedLock lockClient = client.distributedLock();
 *
 *     // 场景 1：单次锁（不可重入）
 *     Lock lock = lockClient.tryLock("order:123", 30_000); // TTL 30s
 *     if (lock != null) {
 *         try {
 *             doBusiness();
 *         } finally {
 *             lockClient.unlock(lock);
 *         }
 *     }
 *
 *     // 场景 2：可重入锁（同一线程多次进入）
 *     Lock lock2 = lockClient.tryLock("resource", 10_000);
 *     Lock lock3 = lockClient.tryLock("resource", 10_000); // 返回新的 Lock 句柄，counter++
 *     lockClient.unlock(lock3);  // counter 仍 > 0，锁未释放
 *     lockClient.unlock(lock2);  // counter 归 0，原子释放
 *
 *     // 场景 3：公平锁（按获取顺序排队）
 *     Lock fair = lockClient.tryLock("fair-resource", 5_000, 3_000); // 等待最多 3s
 * }
 * }</pre>
 *
 * @author zifang
 * @since 1.3.0
 */
public interface DistributedLock extends AutoCloseable {

    /**
     * 尝试获取锁，立即返回（非阻塞）。
     *
     * @param key      锁的 key（任意字符串）
     * @param ttlMs    锁的 TTL（毫秒）。超过此时间未释放或续约，锁自动失效。
     *                 建议设置为业务最长执行时间的 2-3 倍。
     * @return 成功返回 Lock 句柄；key 已存在 / TTL 非法返回 null。
     * @throws IllegalArgumentException ttlMs <= 0 或 key 为 null
     */
    Lock tryLock(String key, long ttlMs);

    /**
     * 尝试获取锁，最多阻塞等待 waitMs 毫秒。
     *
     * @param key      锁的 key
     * @param ttlMs    锁的 TTL（毫秒）
     * @param waitMs   最长等待时间（毫秒）。<= 0 等价于 {@link #tryLock(String, long)}
     * @return 成功返回 Lock 句柄；超时返回 null
     * @throws IllegalArgumentException ttlMs <= 0 或 key 为 null
     */
    Lock tryLock(String key, long ttlMs, long waitMs);

    /**
     * 释放锁。仅释放当前线程/句柄持有的锁（ownerId 匹配），不误删他人锁。
     *
     * @param lock 通过 {@link #tryLock} 获取的句柄
     * @throws IllegalArgumentException lock 为 null 或已被本 client 释放
     * @throws LockReleaseException     服务端异常
     */
    void unlock(Lock lock) throws LockReleaseException;

    /**
     * 续约（延长 TTL）。仅当 lock 仍归属当前 ownerId 时成功。
     *
     * @param lock    锁句柄
     * @param ttlMs   新的 TTL（毫秒）。通常传入原 TTL 或其整数倍。
     * @return true 续约成功；false 锁已被他人持有 / TTL 已过期
     */
    boolean renew(Lock lock, long ttlMs);

    /**
     * 获取当前 key 锁的 ownerId（用于诊断）。
     *
     * @param key 锁的 key
     * @return ownerId（UUID 字符串），key 未被锁时返回 null
     */
    String currentOwner(String key);

    /**
     * 关闭分布式锁客户端，释放所有内部资源（包括 watchdog 线程）。
     */
    @Override
    void close();
}
```

### 2.2 锁句柄 `Lock`

```java
package com.zifang.z.cache.client.lock;

import java.util.Objects;

/**
 * 分布式锁句柄。线程不安全（每个线程应持有自己的实例）。
 *
 * <p>字段：
 * <ul>
 *   <li>key —— 锁的 key</li>
 *   <li>ownerId —— 持有者唯一标识（UUID），用于 unlock/renew 时身份校验</li>
 *   <li>fencingToken —— 单调递增令牌（Long），用于业务侧防"双写"
 *       （参考 Kleppmann "How to do distributed locking"）</li>
 *   <li>acquiredAt —— 获取时间（毫秒时间戳）</li>
 *   <li>ttlMs —— 原始 TTL</li>
 * </ul>
 *
 * @author zifang
 * @since 1.3.0
 */
public final class Lock {

    private final String key;
    private final String ownerId;
    private final long fencingToken;
    private final long acquiredAt;
    private final long ttlMs;

    public Lock(String key, String ownerId, long fencingToken, long ttlMs) {
        this.key = Objects.requireNonNull(key, "key");
        this.ownerId = Objects.requireNonNull(ownerId, "ownerId");
        this.fencingToken = fencingToken;
        this.acquiredAt = System.currentTimeMillis();
        this.ttlMs = ttlMs;
    }

    public String getKey() { return key; }
    public String getOwnerId() { return ownerId; }
    public long getFencingToken() { return fencingToken; }
    public long getAcquiredAt() { return acquiredAt; }
    public long getTtlMs() { return ttlMs; }

    @Override
    public String toString() {
        return "Lock{key='" + key + "', ownerId='" + ownerId
                + "', fencingToken=" + fencingToken
                + ", acquiredAt=" + acquiredAt + ", ttlMs=" + ttlMs + '}';
    }
}
```

### 3.1 tryLock 实现流程

```java
public Lock tryLock(String key, long ttlMs) {
    if (ttlMs <= 0) throw new IllegalArgumentException("ttlMs must be > 0");
    String ownerId = UUID.randomUUID().toString();
    long fencingToken = FENCING_TOKEN.incrementAndGet(); // 全局单调递增
    // value 格式：ownerId|fencingToken 用于 server 端 Lua 校验（可选）
    String value = ownerId + "|" + fencingToken;

    Object resp = client.sendCommand("SET", key, value, "NX", "PX", String.valueOf(ttlMs));
    if (isOk(resp)) {
        return new Lock(key, ownerId, fencingToken, ttlMs);
    }
    return null; // key 已存在
}
```

### 3.2 unlock 实现流程（Lua 原子）

服务端 Lua 脚本 `unlock.lua`（z-cache 启动时通过 `SCRIPT LOAD` 缓存）：

```lua
-- KEYS[1] = lock key
-- ARGV[1] = expected ownerId
-- ARGV[2] = expected fencingToken（可选，0 表示不校验）
local current = redis.call('GET', KEYS[1])
if current == false then
    return -1  -- 锁不存在
end
-- 解析 ownerId|fencingToken
local sep = string.find(current, '|', 1, true)
if not sep then
    return -2  -- value 格式异常
end
local curOwner = string.sub(current, 1, sep - 1)
local curToken = tonumber(string.sub(current, sep + 1))
if curOwner ~= ARGV[1] then
    return -3  -- 不是自己的锁
end
if tonumber(ARGV[2]) > 0 and curToken < tonumber(ARGV[2]) then
    return -4  -- fencing token 过期（已被自己之前的请求作废）
end
redis.call('DEL', KEYS[1])
return 1
```

Java 侧调用：

```java
public void unlock(Lock lock) throws LockReleaseException {
    String sha1 = UNLOCK_SHA; // SCRIPT LOAD 时缓存
    Object resp = client.sendCommand(
        "EVALSHA", sha1, "1",
        lock.getKey(), lock.getOwnerId(), String.valueOf(lock.getFencingToken())
    );
    long result = toLong(resp);
    if (result != 1) {
        throw new LockReleaseException("unlock failed, code=" + result);
    }
}
```

### 3.3 renew 实现流程

```java
public boolean renew(Lock lock, long ttlMs) {
    // 用 Lua 脚本：检查 ownerId 匹配后 SET XX PX 续约
    String sha1 = RENEW_SHA;
    Object resp = client.sendCommand(
        "EVALSHA", sha1, "1",
        lock.getKey(), lock.getOwnerId(), String.valueOf(ttlMs)
    );
    return toLong(resp) == 1;
}
```

服务端 Lua `renew.lua`：

```lua
-- KEYS[1] = lock key, ARGV[1] = ownerId, ARGV[2] = new ttlMs
local current = redis.call('GET', KEYS[1])
if current == false then return 0 end
local sep = string.find(current, '|', 1, true)
if not sep then return 0 end
local curOwner = string.sub(current, 1, sep - 1)
if curOwner ~= ARGV[1] then return 0 end
redis.call('SET', KEYS[1], current, 'PX', tonumber(ARGV[2]))
return 1
```

### 3.4 可重入支持

可重入通过 client 端维护 `ConcurrentHashMap<String, Lock>` 实现：同一 ownerId（同一线程）多次调用 tryLock 时，counter 自增，value 中嵌入 `counter`：

```
value = "ownerId|fencingToken|counter"
```

但这会让 Lua 解析变复杂。**1.3.0 不实现可重入**（保持简单；2.0.0 集群版按需补）。

### 3.5 Watchdog 自动续约

长任务场景下，业务线程可能调用 `tryLock(key, 60_000)` 但实际执行需要 5 分钟。两种选择：

1. **业务侧手动 renew**：业务代码每隔 `ttlMs / 3` 调用 `lockClient.renew(lock, ttlMs)`。
2. **client 侧 watchdog**：`tryLock` 返回时启动一个 `ScheduledExecutorService` 任务，每 `ttlMs / 3` 自动 renew；`unlock` 时取消任务。

**1.3.0 推荐方案 2**（watchdog），因为对业务代码侵入小。watchdog 实现：

```java
class LockWatchdog implements AutoCloseable {
    private final ScheduledExecutorService scheduler =
        Executors.newScheduledThreadPool(2, r -> {
            Thread t = new Thread(r, "z-cache-lock-watchdog");
            t.setDaemon(true);
            return t;
        });

    void scheduleRenew(Lock lock) {
        long interval = lock.getTtlMs() / 3;
        ScheduledFuture<?> f = scheduler.scheduleAtFixedRate(
            () -> {
                try { renew(lock, lock.getTtlMs()); }
                catch (Exception e) { logger.warn("watchdog renew failed", e); }
            },
            interval, interval, TimeUnit.MILLISECONDS);
        renewTasks.put(lock, f);
    }

    void cancel(Lock lock) {
        ScheduledFuture<?> f = renewTasks.remove(lock);
        if (f != null) f.cancel(false);
    }
}
```

### 3.6 fencingToken 机制

`FENCING_TOKEN` 是 client 侧 `AtomicLong`，每次 tryLock 自增。Lock 句柄携带 token，业务侧在写入受保护资源（如 DB UPDATE）时带上 token：

```java
Lock lock = lockClient.tryLock("order:123", 30_000);
if (lock != null) {
    try {
        // DB UPDATE WHERE id=? AND fencing_token < ?
        int rows = jdbc.update(
            "UPDATE orders SET status='PAID', fencing_token=? WHERE id=? AND fencing_token < ?",
            lock.getFencingToken(), 123, lock.getFencingToken());
        if (rows == 0) {
            // 已经被更高 token 的请求写过，放弃
        }
    } finally {
        lockClient.unlock(lock);
    }
}
```

**约束**：fencing token 仅 client 端单调递增，**不能跨进程**。多进程共享锁的场景下，1.3.0 不提供进程级 fencing token（需要服务端 INCR 计数器，留给 2.0.0）。

## 4. 客户端使用示例

### 4.1 单次锁

```java
try (ZCacheClient client = new ZCacheClient("localhost", 16379)) {
    client.connect();
```

## 6. 限制与已知坑

### 6.1 单节点限制

z-cache 1.3.0 仅提供**单节点 Redlock 等价能力**，与 Redis 6.2+ 官方推荐一致。

**真正的 Redlock 需要 ≥3 个独立 master 节点 + 多数派协议**，z-cache 当前没有集群能力，留给 2.0.0。

如果业务侧需要严格 Redlock：
- 部署 ≥3 个独立 z-cache 实例（不同进程、不同机器）；
- 在 client 侧实现 Redlock 协调（向每个实例 SET NX PX，全部成功才算拿到锁）；
- 这是 client 侧能力，不依赖 z-cache 服务端升级。

### 6.2 持久化交互

z-cache 已有 AOF + RDB 持久化，锁 value 会被持久化。

| 持久化策略 | 锁的影响 |
|---|---|
| **AOF everysec** | 崩溃可能丢 1 秒内的 SET/DEL。后果：客户端 unlock 失败（value 已丢失，但客户端以为还在）。Lua 解锁的 ownerId 校验保证不误删他人的锁 ✅ |
| **AOF always** | 无丢失；但性能下降约 30-50%（同步 fsync） |
| **RDB 快照** | BGSAVE 间隔过长，崩溃恢复丢失期间所有锁。建议 `save 900 1` + AOF everysec 配合 |
| **建议**：AOF `everysec` + RDB `save 900 1`，平衡性能与可靠性 |

### 6.3 fencing token 局限

1.3.0 的 fencing token 仅 client 端单调递增，**不能跨进程**。如下场景失效：

- 同一 z-cache 服务端被多个 client 进程连接；
- Client A 拿到 token=1，写 DB；
- Client A GC 停顿 60s，锁过期；
- Client B 拿到 token=2，写 DB；
- Client A 醒来，写 DB（**token=1 < token=2 但没校验**）；
- 数据库出现"双写"。

**业务侧必须用 DB `WHERE fencing_token < ?` 防御**（见 §3.6 示例）。

### 6.4 与 cluster 模式不兼容

z-cache 1.3.0 是单节点。如果未来上集群，锁的 key 会被 hash 到特定 slot；如果业务侧不指定 Hash Tag，单 key 锁在不同 slot 的迁移过程中可能短暂无法访问。1.3.0 单节点无此问题。

### 6.5 Lua EVAL 脚本缓存

z-cache-server 启动时通过 `SCRIPT LOAD` 预加载 unlock.lua 和 renew.lua，返回 SHA1 缓存。client 首次调用 EVALSHA 若返回 NOSCRIPT，自动 fallback 到 EVAL 重试。

### 6.6 watchdog 线程泄漏

`DistributedLock.close()` 必须被调用，否则 watchdog 线程 + ScheduledExecutorService 会泄漏。建议：

- 使用 try-with-resources（接口继承 `AutoCloseable`）；
- Spring 容器中由 `@PreDestroy` 回调关闭；
- 每个 ZCacheClient 实例对应一个 DistributedLock 实例，不要单例化。

## 8. 测试计划（对应 TASK-20260918-005 验收标准）

### 8.1 单元测试（`DistributedLockTest`，至少 5 用例）

1. `testAcquireLock_Success` —— 首次 tryLock 返回非 null Lock
2. `testAcquireLock_FailOnContention` —— 同一 key 第二次 tryLock 返回 null
3. `testUnlock_Success` —— unlock 后第二次 tryLock 成功
4. `testUnlock_FailOnForeignLock` —— 用他人的 ownerId unlock 抛出异常
5. `testRenew_Success` —— renew 后延长 TTL，再 tryLock 仍失败
6. `testRenew_FailOnExpiredLock` —— TTL 过期后 renew 返回 false
7. `testWatchdog_AutoExtend` —— 长任务期间锁不释放（dog 自动 renew）
8. `testClose_ReleasesWatchdog` —— close() 后 watchdog 线程终止

### 8.2 集成测试（`DistributedLockIT`）

- 100 个并发线程 tryLock 同一个 key，期望**恰好 1 个**成功
- 释放后再并发 100 个线程，**下一个**线程可成功

### 8.3 性能基准（JMH）

- 1000 并发线程 tryLock + 立即 unlock 循环
- **目标**：TPS ≥ 20_000，P99 < 5ms（参考调研报告 §4.3）
