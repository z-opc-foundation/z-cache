## 1. 调研背景

z-cache 当前是单节点模式（[README.md](file:///Users/zifang/workplace/ceo_workplace/z-opc-foundation/z-cache/README.md) 中虽然已出现集群模式 YAML 配置示例，但 [z-cache-core/src/main/java/com/zifang/z/cache/core/](file:///Users/zifang/workplace/ceo_workplace/z-opc-foundation/z-cache/z-cache-core/src/main/java/com/zifang/z/cache/core/) 下**完全没有 `cluster`/`replication`/`sentinel` 子包**），无法支撑分布式场景。

需要从三种主流方案中选择：

- **方案 A**：一致性哈希（参考 DynamoDB / Cassandra / Twemproxy）
- **方案 B**：16384 哈希槽映射（参考 Redis Cluster）
- **方案 C**：Codis（基于 ZooKeeper 的 Proxy 层方案）

调研结论将决定 [TASK-20260918-004](../done/2026-09-19/TASK-20260918-004.md) 集群运维手册与后续集群代码实现路径。

## 3. 方案对比

### 3.1 方案 A：一致性哈希 + 虚拟节点

**思路**：key 经过 CRC32/MD5 散列到 `2^32` 环上，节点也映射到环上，key 沿环顺时针找到第一个节点即为归属节点。增加虚拟节点（VN）解决数据倾斜。

#### 评估维度

| 维度 | 数据 / 结论 |
|---|---|
| **数据迁移成本** | 增加 1 节点时，约 `1/N`（N=当前节点数）的 key 需迁移。N=3 时迁移 ~33%；N=100 时 ~1%。 |
| **故障转移** | 节点宕机后，下游节点接管其 hash range；Redis Sentinel 风格需要外挂。z-cache 现状无 Sentinel，**需自研**。 |
| **客户端实现** | 简单 —— 客户端自行计算 key 归属，不需要知道集群拓扑。但**不支持在线 rebalance 时路由动态变化**（虚拟节点权重变更时客户端需感知）。 |
| **与 Redis 协议兼容** | **不兼容** Redis Cluster；客户端不能直接用 Jedis/Lettuce/Redisson 等主流库。 |
| **已有成功案例** | DynamoDB、Cassandra、Twemproxy、Ketama；大规模生产验证。 |
| **对 z-cache 的实现成本** | ~800 行 Java：HashRing + 虚拟节点 + 节点注册 + gossip 心跳 + 客户端 SDK 改造（须用 SDK 计算路由）。 |
| **结论** | **可考虑** |

### 3.2 方案 B：16384 哈希槽映射（Redis Cluster 风格）

**思路**：所有 key 先经 `CRC16(key) mod 16384` 计算 slot，slot 静态绑定到节点。客户端可缓存 slot→node 映射，请求错误时通过 `MOVED` / `ASK` 重定向。

#### 评估维度

| 维度 | 数据 / 结论 |
|---|---|
| **数据迁移成本** | 增加 1 节点时，从其他节点"挪"部分 slot 过来；以 slot 为粒度，**迁移粒度可控**（最小单位是 1 个 slot = 1/N 数据）。Redis 8.4 引入 atomic slot migration 进一步保证迁移一致性（[Redis blog](https://redis.io/blog/atomic-slot-migration/)）。 |
| **故障转移** | 内置：master 宕机时通过 Gossip + 多数派选举自动晋升 replica。故障检测 + failover 整体 ~5-15 秒（受 cluster-node-timeout 配置影响）。 |
| **客户端实现** | **复杂** —— 需要 smart client（Lettuce/Jedis cluster 模式）或简单 client + MOVED 重定向。z-cache-client 当前是简单直连模式，需扩展为 cluster-aware。 |
| **与 Redis 协议兼容** | **完全兼容** Redis Cluster 协议。外部用户可用 Jedis/Lettuce/Redisson 直接连（前提是 z-cache 实现 RESP CLUSTER 子集）。 |
| **16384 这个数字的合理性** | Antirez 解释：16384 slots 在 gossip 心跳包中只需 2KB bitmap（[参考](https://severalnines.com/blog/hash-slot-vs-consistent-hashing-redis/)），避免 65535 时的 8KB 膨胀；最大支持 ~1000 节点，足够大规模集群。 |
| **Hash Tags** | 支持 `{user:1001}.profile` + `{user:1001}.orders` 强制同 slot，解决 CROSSSLOT 限制（MSET/MGET 不能跨 slot）。 |
| **已有成功案例** | Redis 3.0+ 自 2015 年生产验证；AWS ElastiCache、阿里云 Redis 集群版、腾讯云 Redis 均基于此。 |
| **对 z-cache 的实现成本** | ~1500-2000 行 Java：slot 计算 + slot→node 映射 + Gossip 协议（ping/pong/meet/fail/publish）+ 客户端 MOVED 重定向 + slot 迁移命令 + 数据快照迁移。**但有 Redis Cluster 完整规范可参考**。 |
| **结论** | **强烈推荐** |

### 3.3 方案 C：Codis（Proxy-based 方案）

**思路**：在客户端与 Redis 之间架设 Proxy 集群，Proxy 维护 slot→group 映射，客户端只连 Proxy 不知集群。Codis 还依赖 ZooKeeper/etcd 做配置中心。

#### 评估维度

| 维度 | 数据 / 结论 |
|---|---|
| **数据迁移成本** | 以"slot group"为单位迁移（1024 slot 一组），粒度比方案 B 粗；迁移过程 Proxy 自动路由。 |
| **故障转移** | 依赖 HAProxy + Sentinel 风格的外部组件；Codis 自身不负责。 |
| **客户端实现** | **最简单** —— 客户端只连 Proxy，完全无需感知集群。但 Proxy 是新单点（虽可水平扩展）。 |
| **与 Redis 协议兼容** | 客户端侧 RESP 完全兼容；Codis 服务端是非标准 Redis（用 RocksDB / 自研存储）。 |
| **维护活跃度** | Codis 最近一次发版是 2022 年（[GitHub CodisLabs/codis](https://github.com/CodisLabs/codis)），社区活跃度低。Codis 3.x 计划用 Rust 重写但未发布。 |
| **依赖 ZooKeeper** | Codis 强依赖 ZK 做配置中心。z-cache 当前无 ZK 集成；引入 ZK 增加**额外组件**（部署、监控、可用性）。 |
| **是否走 Go** | Codis Proxy 是 Go 写的，与 z-cache（Java）异构；引入 Codis 等于把"集群能力外包给异构系统"，调试、追踪、二次开发成本高。 |
| **对 z-cache 的架构合理性** | **差**：z-cache 定位是"Redis 兼容的内存数据库"，引入 Proxy 层等于承认"z-cache-server 单点能力不够"——削弱产品定位。 |
| **结论** | **不推荐** |

## 4. 结论

### 4.1 推荐方案：**方案 B（16384 哈希槽 + Redis Cluster 风格）**

**理由**（按权重排序）：

1. **与 z-cache 自身定位高度契合**：z-cache 是"Redis 兼容的内存数据库"，采用 Redis Cluster 风格的协议让用户心智模型一致；现有 RESP 命令解析可直接复用；客户端切换 cluster 模式只是 SDK 升级。
2. **生态完全兼容**：外部用户用 Jedis/Lettuce/Redisson 即可连接，零额外适配；[TASK-20260918-007 Stream 消费组]（已完成协议设计）和 [TASK-20260918-008 持久化] 都自然支持 cluster 模式（按 slot 维度分摊）。
3. **实现有完整规范可参考**：[Redis Cluster Specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/) 涵盖所有边界场景（节点握手、心跳、故障检测、slot 迁移、复制）；Antirez 团队 10 年迭代打磨。
4. **迁移粒度可控**：以 slot 为单位（1/16384）做迁移，比一致性哈希以"key 粒度"更稳定（迁移过程中不影响在线请求）。
5. **Hash Tags 解决 CROSSSLOT**：MSET/MGET 多 key 操作的限制通过 `{...}` 强制同 slot 解决，**业务侧无感知**。
6. **可演进**：1.3.0 单 master 单 replica 集群起步；后续可平滑升级到 cluster-tier（多 master 多 replica）+ 跨地域复制。

### 4.2 不推荐方案：**方案 A（一致性哈希）**

**理由**：

- 不兼容 Redis Cluster 协议，外部用户用主流 Java 客户端必须切换 SDK；
- 故障转移需外挂 Sentinel 风格组件，增加额外模块；
- 迁移粒度细到 key 级别，大集群 rebalance 时流量毛刺明显。

### 4.3 不推荐方案：**方案 C（Codis）**

**理由**：

- Codis Proxy 是 Go 写的，z-cache 是 Java，**异构系统**调试 / 追踪 / 二次开发成本高；
- Codis 强依赖 ZooKeeper/etcd 做配置中心，**新增组件**；
- Codis 社区活跃度低（最近发版 2022 年）；
- 架构层面削弱 z-cache-server 自身定位（"为什么需要 Proxy？因为我自己的集群实现不够好"）。

```

│   ├── 至少 3 master + 3 replica 起步（保证 quorum）
│   ├── 网络要求：节点间互联带宽 ≥ 1Gbps，延迟 < 1ms（同机房）

├── 3. 在线扩缩容
│   ├── 增加 master：CLUSTER MEET 新节点 → RESHARD 迁移 slot

├── 4. 故障转移演练
│   ├── master 宕机 → 30 秒内自动晋升 replica（多数派投票）

│   ├── cluster_state（ok / fail）
│   ├── cluster_slots_assigned（应 = 16384）
│   ├── cluster_known_nodes
│   ├── cluster_size（master 数）
│   └── 每个 master 的 used_memory / ops_per_sec
└── 6. 常见故障应急清单（5+ 场景）
    ├── 节点失联 → cluster-node-timeout 内可恢复，超时则触发 failover
    ├── 多数 master 宕机 → 集群 fail，需手动恢复
    ├── slot 未全覆盖 → CLUSTER SLOTS 检查并修复
    └── ...
```

### 4.5 对后续集群代码任务（1.3.0 范围外但需立项）的具体指导

建议拆解为以下 code 任务（每个单独 task）：

1. **slot 计算与本地路由**：在 CommandHandler 入口处增加 `CRC16(key) mod 16384`，本地命中则处理，否则按 slot→node 映射转发。
2. **Gossip 协议**：节点间 ping/pong/ping 定时心跳；ping 携带已知节点列表与 slot 分布。
3. **MOVED/ASK 重定向**：当前节点不负责该 slot 时返回 `MOVED slot target_node`；迁移过程中返回 `ASK`。
4. **CLUSTER 子集命令**：CLUSTER INFO / CLUSTER NODES / CLUSTER SLOTS / CLUSTER KEYSLOT / CLUSTER MEET / CLUSTER ADDSLOTS / CLUSTER SETSLOT。
5. **slot 迁移**：MIGRATE 命令实现 + 客户端 SDK 配合。
6. **主从复制**：基于已有 AOF/RDB 实现 replica 同步；REPLICAOF 命令。
7. **故障检测与 failover**：基于 Gossip 主观下线 + 多数派客观下线 + replica 选举。

## 5. 风险与限制

1. **16384 不是越多越好**：选 16384 是 Antirez 在带宽（gossip 心跳 2KB）与扩展性（~1000 节点）间的平衡；如果 z-cache 计划支持 1000+ 节点集群，可沿用；如只支持几十节点，一致性哈希更轻量（但已不是 z-cache 的定位）。
2. **单 key 原子 vs 多 key 原子**：Redis Cluster 牺牲了 multi-key 操作的全局原子性（受 CROSSSLOT 限制）。需要靠 Hash Tags + Lua 脚本组合解决。
3. **客户端兼容性成本**：z-cache-client 当前是简单直连模式，必须升级为 cluster-aware（缓存 slot→node 映射 + 处理 MOVED）。这是 1.3.0 之外的**额外工作量**。
4. **ZSK 当前版本（JDK 8）vs Redis Cluster 客户端生态**：Jedis/Lettuce/Redisson 都要求 JDK 11+；如 z-cache 坚持 JDK 8，需自研 cluster-aware client。
5. **大 key 迁移**：单个 slot 如果持有大 key（如 100MB string），slot 迁移期间会阻塞该 slot 的请求。建议 z-cache 限制 max 单 value size（默认 1MB）。
