## 1. 部署前置条件

### 1.1 集群规模建议

| 阶段 | 节点数 | 副本数 | 适用场景 |
|---|---|---|---|
| 最小生产 | 3 master + 3 replica | 1 | 多数派可用（容忍 1 master + 1 replica 同时故障）|
| 推荐生产 | 6 master + 6 replica | 1 | 高可用 + 在线扩缩容 |
| 大规模 | 16 master + 16 replica | 1 | >100GB 数据，单 master 内存压力 |

**注意**：master 数必须 ≥ 3 才能形成 quorum；replica 数 ≥ 1 提供故障转移。

### 1.2 机器规格

每个 master 节点：

| 资源 | 最低 | 推荐 |
|---|---|---|
| CPU | 4 核 | 8 核（IO 线程 + Worker 线程 + Gossip 线程）|
| 内存 | 8 GB | 32 GB（按 1:1 数据:内存规划）|
| 磁盘 | 100 GB SSD | 500 GB NVMe（AOF + RDB 持久化）|
| 网卡 | 1 Gbps | 10 Gbps（节点间 Gossip + slot 迁移）|

### 1.3 网络要求

- **节点间互联**：同机房延迟 < 1ms，带宽 ≥ 1 Gbps（推荐 10 Gbps）
- **客户端到节点**：跨可用区部署时延迟 < 5ms；客户端 SDK 自动就近连接
- **端口开放**：

| 端口 | 用途 |
|---|---|
| 16379（业务端口） | RESP 客户端连接 |
| 16379 + 10000 = 26379（cluster bus） | 节点间 Gossip 通信（Redis Cluster 默认 +10000）|

### 1.4 端口规划示例

| 节点 | 业务端口 | Cluster Bus | 角色 |
|---|---|---|---|
| node-1 | 16379 | 26379 | master / 持有 slots 0-5460 |
| node-2 | 16379 | 26379 | master / 持有 slots 5461-10922 |
| node-3 | 16379 | 26379 | master / 持有 slots 10923-16383 |
| node-4 | 16379 | 26379 | replica of node-1 |
| node-5 | 16379 | 26379 | replica of node-2 |
| node-6 | 16379 | 26379 | replica of node-3 |

所有节点业务端口相同，但 cluster bus 端口必须不同（每个节点独立）。

## 2. 集群初始化流程

### 2.1 配置文件（每个节点独立）

```yaml
# /etc/z-cache/cluster-node.conf
cluster:
  enabled: true
  node-id: auto                     # 首次启动自动生成 40 字符 hex
  cluster-config-file: nodes.conf   # 集群拓扑持久化文件
  cluster-node-timeout: 5000        # 节点超时时间（ms）
  cluster-port: 26379               # cluster bus 端口（业务端口 + 10000）
  cluster-require-full-coverage: yes
  cluster-replica-validity-factor: 10  # replica 失联超过 10*timeout 强制 failover

server:
  port: 16379
  bind: 0.0.0.0

persistence:
  rdb-enabled: true
  rdb-save-rules:
    - "900 1"
    - "300 10"
    - "60 10000"
  aof-enabled: true
  aof-fsync: everysec
  aof-rewrite-threshold: 64mb

# 节点间认证（生产必开）
security:
  cluster-auth: z-cache-cluster-pass-2026Q4
  client-auth: z-cache-client-pass-2026Q4
```

### 2.2 启动所有节点

```bash
#!/bin/bash
# /usr/local/bin/start-zcache-node.sh
set -euo pipefail

NODE_ID="${1:?Usage: start-zcache-node.sh <node-name>}"
CONFIG_FILE="/etc/z-cache/${NODE_ID}.conf"
DATA_DIR="/var/lib/z-cache/${NODE_ID}"

mkdir -p "${DATA_DIR}"
systemctl start "z-cache@${NODE_ID}.service"

# 等待节点就绪
for i in {1..30}; do
    if redis-cli -h "${NODE_ID}" -p 16379 ping 2>/dev/null | grep -q PONG; then
        echo "${NODE_ID} is up"
        exit 0
    fi
    sleep 1
done

echo "ERROR: ${NODE_ID} failed to start within 30s"
journalctl -u "z-cache@${NODE_ID}.service" --no-pager -n 50
exit 1
```

在每台机器上执行：

```bash
# node-1
ssh node-1 'start-zcache-node.sh node-1'
ssh node-2 'start-zcache-node.sh node-2'
ssh node-3 'start-zcache-node.sh node-3'
ssh node-4 'start-zcache-node.sh node-4'
ssh node-5 'start-zcache-node.sh node-5'
ssh node-6 'start-zcache-node.sh node-6'
```

### 2.3 节点握手 + 创建集群

使用 `redis-cli --cluster create`（z-cache 1.3.0 起兼容 Redis Cluster 协议，可用 redis-cli 7.x 管理工具）：

```bash
# 在任意一台客户端机器上执行
redis-cli --cluster create \
    node-1:16379 node-2:16379 node-3:16379 \
    node-4:16379 node-5:16379 node-6:16379 \
    --cluster-replicas 1 \
    --cluster-yes
```

预期输出：

```
>>> Performing hash slots allocation on 6 nodes...
Master[0] -> Slots 0 - 5460
Master[1] -> Slots 5461 - 10922
Master[2] -> Slots 10923 - 16383
Adding replica node-4:16379 to node-1:16379
Adding replica node-5:16379 to node-2:16379
Adding replica node-6:16379 to node-3:16379
>>> Performing Cluster Check (using node node-1:16379)
[OK] All nodes agree about slots configuration.
>>> Check for open slots...
>>> Check slots coverage...
[OK] All 16384 slots covered.
```

### 2.4 验证集群状态

```bash
# 集群整体状态
redis-cli -h node-1 -p 16379 cluster info
# 期望输出：cluster_state:ok

# 节点拓扑
redis-cli -h node-1 -p 16379 cluster nodes
# 期望输出：6 行，每行包含 node-id + address:port@bus + flags + master/replica + slots

# slot 分布
redis-cli -h node-1 -p 16379 cluster slots
```

## 3. 在线扩缩容

### 3.1 增加 master 节点

**场景**：现有 3 master 集群写入压力升高，新增 1 master。

#### 步骤

1. **启动新节点**（node-7），配置同 §2.1，但 `node-id` 自动生成。
2. **加入集群**（在 node-1 上执行）：

    ```bash
    redis-cli -h node-1 -p 16379 cluster meet node-7 16379
    redis-cli -h node-7 -p 16379 cluster replicate <node-1-id>  # 先挂为 replica
    ```

3. **slot 重分配**（从 3 个老 master 各迁 1/4 slot 到新 master）：

    ```bash
    redis-cli --cluster reshard node-1:16379 \
        --cluster-from all \
        --cluster-to <node-7-id> \
        --cluster-slots 4096 \
        --cluster-yes
    ```

    预期：自动从 3 个老 master 各迁出 1365 slot 到 node-7；迁移过程中集群继续服务。

4. **可选**：将 node-7 提升为 master（如果之前是 replica 挂载）：

    ```bash
    redis-cli -h node-7 -p 16379 cluster failover force
    ```

5. **验证**：

    ```bash
    redis-cli -h node-1 -p 16379 cluster info | grep cluster_size
    # 期望：cluster_size:4（4 个 master）
    ```

### 3.2 摘除 master 节点

**场景**：节点老化，需摘除 node-3。

#### 步骤

1. **迁移 slot 到其他 master**（node-3 上的 slots 10923-16383 全部迁到 node-1）：

    ```bash
    redis-cli --cluster reshard node-1:16379 \
        --cluster-from <node-3-id> \
        --cluster-to <node-1-id> \
        --cluster-slots 5461 \
        --cluster-yes
    ```

2. **迁移 node-3 的 replica**：将 node-6 重新指向 node-1：

    ```bash
    redis-cli -h node-6 -p 16379 cluster replicate <node-1-id>
    ```

3. **从集群中下线 node-3**：

    ```bash
    redis-cli -h node-1 -p 16379 cluster forget <node-3-id>
    redis-cli -h node-2 -p 16379 cluster forget <node-3-id>
    # 在所有其他节点上重复 forget（cluster forget 只影响当前连接）
    ```

4. **停止 node-3 进程**：

    ```bash
    ssh node-3 'systemctl stop z-cache@node-3.service'
    ```

5. **验证**：

    ```bash
    redis-cli -h node-1 -p 16379 cluster nodes | grep node-3
    # 期望：空输出
    ```

### 3.3 紧急扩容脚本（运维模板）

```bash
#!/bin/bash
# /usr/local/bin/zcache-add-node.sh
# 用法：zcache-add-node.sh <new-node-ip> <new-node-name>
set -euo pipefail

NEW_IP="${1:?Usage: zcache-add-node.sh <ip> <name>}"
NEW_NAME="${2:?Usage: zcache-add-node.sh <ip> <name>}"

# 1. 启动新节点（依赖 Ansible/Puppet 部署）
echo ">>> Starting ${NEW_NAME}..."
ssh "${NEW_IP}" "start-zcache-node.sh ${NEW_NAME}"

# 2. 加入集群
ANY_OLD_NODE=$(redis-cli -h node-1 -p 16379 cluster nodes | grep master | head -1 | awk '{print $2}' | cut -d: -f1)
echo ">>> Meeting ${NEW_NAME} via ${ANY_OLD_NODE}..."
redis-cli -h "${ANY_OLD_NODE}" -p 16379 cluster meet "${NEW_IP}" 16379

# 3. 等待 meet 成功
sleep 5

# 4. 计算应迁 slot 数（当前 master 数 / (当前 master 数 + 1)）
NEW_ID=$(redis-cli -h "${ANY_OLD_NODE}" -p 16379 cluster nodes | grep "${NEW_IP}" | awk '{print $1}')
echo ">>> ${NEW_NAME} joined as ${NEW_ID}"

# 5. 提示运维人员手动 reshard（不可全自动）
echo ""
echo "=========================================="
echo "请执行 slot 重新分配："
echo "redis-cli --cluster reshard ${ANY_OLD_NODE}:16379 \\"
echo "    --cluster-from all \\"
echo "    --cluster-to ${NEW_ID} \\"
echo "    --cluster-slots <N> \\"
echo "    --cluster-yes"
echo "=========================================="
```

## 4. 故障转移演练

### 4.1 master 故障转移（自动）

**演练**：手动 kill node-1 master，验证 node-4 replica 自动晋升。

```bash
# 1. 模拟 master 宕机
ssh node-1 'systemctl stop z-cache@node-1.service'

# 2. 观察 cluster 状态变化（30s 内）
watch -n 1 'redis-cli -h node-2 -p 16379 cluster nodes | grep node-1'

# 3. 期望行为：
# - 0~5s：node-1 标记为 "master,fail?"
# - 5~10s：其他 master 投票达成 quorum，node-1 标记为 "master,fail"
# - 10~15s：node-4 replica 触发 failover
# - 15s 后：node-4 标记为 "master"，接管 node-1 的 slots

# 4. 验证读写
redis-cli -h node-2 -p 16379 set test:failover "hello"
redis-cli -h node-4 -p 16379 get test:failover
# 期望：返回 "hello"
```

### 4.2 replica 故障（无 failover）

**演练**：手动 kill node-4 replica。

```bash
ssh node-4 'systemctl stop z-cache@node-4.service'
# 观察：node-4 标记为 "slave,fail?"
# 影响：node-1 失去 replica 保护，集群仍可读写（多数派 quorum 未破坏）
# 恢复：ssh node-4 'systemctl start z-cache@node-4.service' 自动重连
```

### 4.3 多数 master 同时故障（集群 fail）

**演练**：kill node-1 + node-2 master。

```bash
ssh node-1 'systemctl stop z-cache@node-1.service'
ssh node-2 'systemctl stop z-cache@node-2.service'

# 观察：
redis-cli -h node-3 -p 16379 cluster info
# 期望：cluster_state:fail

# 写入测试
redis-cli -h node-3 -p 16379 set test "value"
# 期望：(error) CLUSTERDOWN The cluster is down

# 恢复：依次启动 node-1, node-2
ssh node-1 'systemctl start z-cache@node-1.service'
ssh node-2 'systemctl start z-cache@node-2.service'
# 等 30s 后 quorum 恢复，集群自动恢复 ok
```

### 4.4 故障转移时间指标

| 阶段 | 期望耗时 | 配置参数 |
|---|---|---|
| 主观下线（单个节点发现 node-1 失联）| < 5s | `cluster-node-timeout = 5000` |
| 客观下线（多数派确认）| < 10s | 同上 |
| Replica 选举 + 晋升 | < 5s | 由 replica 自行决定 |
| **总故障转移时间** | **15-20s** | — |

生产建议：客户端重试机制覆盖 30s 故障窗口。

## 5. 监控指标清单

### 5.1 集群级指标（采集自 INFO / CLUSTER INFO）

| 指标名 | 类型 | 告警阈值 | 含义 |
|---|---|---|---|
| `cluster_state` | gauge (0/1) | = 0 立即告警 | 集群是否健康 |
| `cluster_slots_assigned` | gauge | < 16384 告警 | 已分配 slot 数 |
| `cluster_slots_ok` | gauge | < cluster_slots_assigned 告警 | 处于 OK 状态的 slot 数 |
| `cluster_slots_pfail` | gauge | > 0 警告 | 处于"可能失败"状态的 slot 数 |
| `cluster_slots_fail` | gauge | > 0 严重 | 处于"失败"状态的 slot 数 |
| `cluster_known_nodes` | gauge | 期望值的 ±10% 告警 | 集群已知节点数 |
| `cluster_size` | gauge | < 期望值告警 | 集群 master 数 |

### 5.2 节点级指标（每个 master 采集）

| 指标名 | 类型 | 告警阈值 | 含义 |
|---|---|---|---|
| `used_memory` | gauge | > maxmemory 80% 警告 | 已用内存字节数 |
| `used_memory_rss` | gauge | > maxmemory 1.5x 告警 | 操作系统 RSS（含碎片）|
| `mem_fragmentation_ratio` | gauge | > 1.5 警告 / > 2.0 严重 | 内存碎片率 |
| `connected_clients` | gauge | > maxclients 80% 警告 | 当前客户端连接数 |
| `blocked_clients` | gauge | > 100 警告 | 阻塞命令客户端数 |
| `instantaneous_ops_per_sec` | gauge | 趋势下降 50% 告警 | 当前 OPS |
| `keyspace_hits` / `keyspace_misses` | counter | hit rate < 90% 警告 | 缓存命中率 |
| `latest_fork_usec` | gauge | > 1000000（1s）警告 | 最近 fork 耗时（影响 BGSAVE 阻塞）|
| `rdb_last_save_status` | gauge (0/1) | = 0 警告 | 最近 RDB 持久化是否成功 |
| `aof_last_rewrite_status` | gauge (0/1) | = 0 警告 | 最近 AOF 重写是否成功 |

## 6. 常见故障应急清单

### 6.1 节点失联

**症状**：某个 master 节点在 `cluster nodes` 输出中显示 `master,fail?` 或 `master,fail`，客户端连接到此节点的请求返回 `MOVED` 或超时。

**应急 SOP**：

```bash
# 1. 确认进程状态
ssh <node-ip> 'systemctl status z-cache@<node-name>.service'

# 2. 检查网络连通性
redis-cli -h <any-healthy-node> -p 16379 ping

# 3. 检查日志
ssh <node-ip> 'journalctl -u z-cache@<node-name>.service --no-pager -n 100'

# 4. 如进程崩溃，重启
ssh <node-ip> 'systemctl restart z-cache@<node-name>.service'

# 5. 等 30s 后检查 cluster 状态
redis-cli -h <any-healthy-node> -p 16379 cluster info | grep cluster_state
# 期望：cluster_state:ok
```

### 6.2 多数 master 同时宕机（cluster fail）

**症状**：`cluster info` 返回 `cluster_state:fail`，所有写入返回 `CLUSTERDOWN`。

**应急 SOP**：

```bash
# 1. 立即识别宕机节点
redis-cli -h <any-surviving-node> -p 16379 cluster nodes | grep ",fail"

# 2. 按依赖顺序恢复（先恢复 master）
for node in <failed-master-list>; do
    echo ">>> Restarting ${node}..."
    ssh "${node}" 'systemctl start z-cache@'"${node}"'.service'
    sleep 10  # 等节点稳定
done

# 3. 等待 quorum 恢复（30-60s）
for i in {1..60}; do
    STATE=$(redis-cli -h <any-node> -p 16379 cluster info | grep cluster_state | cut -d: -f2 | tr -d '\r')
    if [ "${STATE}" = "ok" ]; then
        echo "Cluster recovered in ${i}s"
        break
    fi
    sleep 1
done

# 4. 验证
redis-cli -h <any-node> -p 16379 set test:recovery "value"
```

**重要**：不要在 `cluster_state:fail` 时手动修改 slot 分配；等 quorum 自然恢复。

### 6.3 slot 未全覆盖（16384 < 全部）

**症状**：`cluster info` 中 `cluster_slots_assigned < 16384`。

**应急 SOP**：

```bash
# 1. 找出未分配的 slot
redis-cli -h <any-node> -p 16379 cluster slots | \
    awk '{print $1, $2}' | sort -u | \
    awk -F'[][]' '{print $2}' | sort -n > assigned.txt
seq 0 16383 > all.txt
comm -23 all.txt assigned.txt > unassigned.txt

# 2. 对每个未分配 slot，强制 assign 到任意 master
for slot in $(head -20 unassigned.txt); do
    TARGET=$(redis-cli -h <any-node> -p 16379 cluster nodes | grep master | head -1 | awk '{print $1}')
    redis-cli -h <node-holding-${TARGET}> -p 16379 cluster addslots ${slot}
done
```

### 6.4 客户端持续收到 MOVED 重定向

**症状**：客户端日志大量 `MOVED 1234 node-x:16379`，业务延迟升高。

**应急 SOP**：

```bash
# 1. 检查客户端 SDK 版本（是否 cluster-aware）
#    Lettuce: 升级到 6.x+
#    Jedis: 升级到 4.x+ 并启用 JedisCluster
#    z-cache-client: 升级到 1.3.0+（支持 cluster 模式）

# 2. 如 SDK 已支持 cluster 模式但仍报错：
#    - 客户端缓存的 slot→node 映射过期
#    - 重启客户端进程，强制重新发现拓扑

# 3. 排查服务端：
redis-cli -h <node> -p 16379 cluster slots | head
# 确认 slot→node 映射正确
```

### 6.5 内存接近上限

**症状**：`used_memory` > `maxmemory` 80%，开始触发淘汰。

**应急 SOP**：

```bash
# 1. 查看各 db key 数
redis-cli -h <node> -p 16379 info keyspace

# 2. 识别大 key（>1MB）
redis-cli -h <node> -p 16379 --bigkeys

# 3. 临时扩容（在线添加 master，参见 §3.1）
# 4. 长期：调整 maxmemory-policy / 清理无用 key / 业务侧优化

# 5. 如内存已 100% 且写入报错：
redis-cli -h <node> -p 16379 info memory | grep maxmemory_policy
# 考虑改为 allkeys-lru（默认 noeviction）
```

### 6.6 AOF 文件膨胀

**症状**：磁盘占用快速增长，`aof_current_size` 持续上升。

**应急 SOP**：

```bash
# 1. 手动触发 AOF 重写
redis-cli -h <node> -p 16379 bgrewriteaof

# 2. 监控重写进度
watch -n 1 'redis-cli -h <node> -p 16379 info persistence | grep aof_rewrite'

# 3. 调优参数（下次启动生效）
#    auto-aof-rewrite-percentage: 100（AOF 文件比上次重写增长 100% 触发）
#    auto-aof-rewrite-min-size: 64mb（最小重写文件大小）
```

### 6.7 Gossip 风暴（网络抖动）

**症状**：节点间 ping/pong 频率异常升高，cluster bus 流量 > 100Mbps。

**应急 SOP**：

```bash
# 1. 检查网络设备（交换机、网卡）
# 2. 调优 Gossip 参数：
#    cluster-node-timeout: 5000 → 10000（放宽超时）
# 3. 排查是否节点数过多（建议 < 100）
```

## 7. 备份与恢复

### 7.1 备份策略

| 备份方式 | 频率 | 保留期 | 适用场景 |
|---|---|---|---|
| RDB 快照 | 每 6 小时 | 7 天 | 日常备份 |
| AOF 文件 | 持续 | 7 天 | 增量恢复 |
| 全量集群 dump（业务级）| 每天 | 30 天 | 重大变更前 |

### 7.2 自动备份脚本

```bash
#!/bin/bash
# /usr/local/bin/zcache-backup.sh
# 用法：在 cron 中运行：0 */6 * * * /usr/local/bin/zcache-backup.sh
set -euo pipefail

BACKUP_ROOT="/var/backups/z-cache"
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
BACKUP_DIR="${BACKUP_ROOT}/${TIMESTAMP}"
RETENTION_DAYS=7

# 遍历所有 master 节点（从 cluster nodes 解析）
NODES=$(redis-cli -h node-1 -p 16379 cluster nodes | grep master | awk '{print $2}' | cut -d: -f1)

mkdir -p "${BACKUP_DIR}"

for node in ${NODES}; do
    echo ">>> Backing up ${node}..."
    redis-cli -h "${node}" -p 16379 save  # 阻塞 save（保证一致性）
    DATA_DIR="/var/lib/z-cache/${node}"
    rsync -az "${DATA_DIR}/dump.rdb" "${BACKUP_DIR}/${node}.rdb"
done

# 清理过期备份
find "${BACKUP_ROOT}" -maxdepth 1 -type d -mtime +${RETENTION_DAYS} -exec rm -rf {} +

echo "Backup completed: ${BACKUP_DIR}"
```

### 7.3 灾难恢复（整个集群重建）

```bash
#!/bin/bash
# /usr/local/bin/zcache-restore.sh
# 用法：zcache-restore.sh <backup-dir>
set -euo pipefail

BACKUP_DIR="${1:?Usage: zcache-restore.sh <backup-dir>}"

# 1. 停止所有 z-cache 节点
for node in node-1 node-2 node-3 node-4 node-5 node-6; do
    ssh "${node}" 'systemctl stop z-cache@'"${node}"'.service' || true
done

# 2. 清空数据目录（避免残留）
for node in node-1 node-2 node-3 node-4 node-5 node-6; do
    ssh "${node}" 'rm -rf /var/lib/z-cache/'"${node}"'/*'
done

# 3. 恢复 RDB 文件（按节点）
for rdb in "${BACKUP_DIR}"/*.rdb; do
    node=$(basename "${rdb}" .rdb)
    scp "${rdb}" "${node}:/var/lib/z-cache/${node}/dump.rdb"
done

# 4. 启动节点
for node in node-1 node-2 node-3 node-4 node-5 node-6; do
    ssh "${node}" 'systemctl start z-cache@'"${node}"'.service'
done

# 5. 等待 30s，让节点重新握手
sleep 30

# 6. 验证集群
redis-cli -h node-1 -p 16379 cluster info
```

## 9. 安全规范

### 9.1 认证

**强制要求**（生产环境）：

- **cluster bus 认证**：所有节点间通信必须通过 `cluster-auth` 密码认证
- **客户端认证**：所有客户端连接必须通过 `requirepass` 密码认证
- **TLS 加密**（1.3.0 内可选，2.0.0 强制）：业务端口 + cluster bus 都启用 TLS

### 9.2 网络隔离

- cluster bus 端口（26379）**禁止暴露在公网**，仅允许集群节点间互通
- 业务端口（16379）通过防火墙限制只允许应用服务器网段访问
- 数据库服务器、应用服务器、运维堡垒机三层网络隔离

### 9.3 凭证管理

```bash
# ❌ 禁止：密码硬编码在配置文件
requirepass: mypassword123

# ✅ 正确：通过环境变量或密码文件
requirepass: ${ZCACHE_PASSWORD}              # 启动时由 systemd 注入
# 或
requirepass-file: /etc/z-cache/auth.pass     # 密码文件，权限 600

# systemd unit 示例
# /etc/systemd/system/z-cache@.service.d/override.conf
[Service]
EnvironmentFile=/etc/z-cache/z-cache.env     # 含 ZCACHE_PASSWORD=xxx
```

### 9.4 审计日志

所有集群管理操作（cluster meet / reshard / failover / forget）必须通过审计日志记录：

```bash
# /etc/audit/rules.d/z-cache.rules
-w /etc/z-cache/ -p wa -k zcache_config_change
-w /usr/bin/redis-cli -p x -k zcache_admin
```

## 10. 升级与回滚

### 10.1 滚动升级流程

**目标**：从 z-cache 1.2.x 升级到 1.3.0，零停机。

```bash
#!/bin/bash
# /usr/local/bin/zcache-rolling-upgrade.sh
set -euo pipefail

OLD_VERSION="1.2.5"
NEW_VERSION="1.3.0"

# 1. 先升级 replica（无写入压力）
for node in node-4 node-5 node-6; do
    echo ">>> Upgrading replica ${node}..."
    ssh "${node}" "systemctl stop z-cache@${node}.service"
    ssh "${node}" "yum install -y z-cache-${NEW_VERSION}"
    ssh "${node}" "systemctl start z-cache@${node}.service"
    
    # 等待 replica 同步追上 master
    sleep 10
    LAG=$(redis-cli -h "${node}" -p 16379 info replication | grep master_last_io_seconds | cut -d: -f2 | tr -d '\r')
    if [ "${LAG}" -gt 5 ]; then
        echo "ERROR: ${node} lag is ${LAG}s, aborting"
        exit 1
    fi
done

# 2. 触发 replica failover（让升级后的 replica 升为 master）
echo ">>> Failing over to upgraded replicas..."
for node in node-4 node-5 node-6; do
    redis-cli -h "${node}" -p 16379 cluster failover force
done

# 3. 升级原 master（现在已经是 replica）
sleep 30  # 等 failover 完成
for node in node-1 node-2 node-3; do
    echo ">>> Upgrading former master ${node}..."
    ssh "${node}" "systemctl stop z-cache@${node}.service"
    ssh "${node}" "yum install -y z-cache-${NEW_VERSION}"
    ssh "${node}" "systemctl start z-cache@${node}.service"
done

# 4. 验证
redis-cli -h node-1 -p 16379 cluster info | grep cluster_state
```

### 10.2 回滚

如升级后出现严重问题：

```bash
# 1. 在所有节点上回滚版本
for node in node-1 node-2 node-3 node-4 node-5 node-6; do
    ssh "${node}" "systemctl stop z-cache@${node}.service"
    ssh "${node}" "yum downgrade -y z-cache-${OLD_VERSION}"
    ssh "${node}" "systemctl start z-cache@${node}.service"
done

# 2. 验证 cluster 状态
redis-cli -h node-1 -p 16379 cluster info
```

**注意**：回滚**保留数据**，不重放 AOF（避免新版本写入的数据格式不兼容老版本）。如新版本有数据格式变更，回滚后必须从备份恢复。
